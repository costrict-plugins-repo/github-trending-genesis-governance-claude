# Agent Model — genesis-governance

This document explains the conceptual model behind the agent definitions generated by `genesis-governance` in Phase 4b. It is written for humans who want to understand, extend, or customize the generated agents.

---

## What are agents?

In Claude Code, an agent is a specialized subprocess invoked from the main instance to handle a specific type of work. Each agent:

- Has a defined **scope** (which files it can touch)
- Has a defined **model** (Opus for design, Sonnet for implementation, Haiku for config)
- Has explicit **anti-patterns** (what it must NOT do)
- Operates with **full context isolation** — it doesn't inherit the main conversation

Without agents, the main Claude Code instance handles everything — no scope enforcement, no model routing, no specialization. With agents, each type of work goes to a subprocess that knows exactly what it's responsible for and what it isn't.

---

## The 3-layer model

genesis-governance generates agents in three layers, from generic to specific:

```
Tier 1 — Universal (always generated, 6 agents)
  ↓ always present in every project
Tier 2 — Optional (activated by intake signals, up to 11 agents)
  ↓ present only when the project's stack/risk profile requires them
Tier 3 — Domain (generated ad-hoc from L2 critical path, 0-3 agents)
  ↓ specific to the project's business domain
```

The result: a fintech project with high security risk and PostgreSQL gets ~11 agents. A simple B2B SaaS with no DB gets ~7. A project with a specialized prediction engine might get 15+.

---

## Tier 1 — Universal agents

These 6 agents are always generated, regardless of project type:

| Agent | Model | Role |
|-------|-------|------|
| `architect` | Opus | Architectural decisions, spec conflicts, Stage 0-2 design. Never writes code. |
| `backend-engineer` | Sonnet | Implements/modifies backend packages and server-side code. |
| `frontend-engineer` | Sonnet | Implements/modifies frontend components, hooks, styles. |
| `git-ops` | Haiku | Git commits, docs, configs, dependencies, CI YAML. Zero-ambiguity operations only. |
| `governance-auditor` | Sonnet | Periodic governance audits: build health, spec coverage, registry coherence, git status. |
| `spec-writer` | Sonnet | Writes and updates specification documents following SDD methodology. |

**Why these 6?** Every non-trivial project needs architecture design, backend + frontend implementation, git operations, ongoing governance, and spec authoring. These are universal workflow roles regardless of domain.

## Tier 2 — Optional agents

These agents are activated by signals from the intake. The model evaluates L3 flags, L4 risk dimensions, and L5 stack before deciding which to generate.

### Activation table

| Activation signal | Agent generated | Why |
|-------------------|----------------|-----|
| L3: `qa_rigor = HIGH` | `test-engineer` | Separates test authorship from implementation to prevent convenience updates |
| L5: DB in stack | `database-engineer` | Schema migrations require a dedicated scope with DROP confirmation gates |
| L3: `has_infra_complexity = true` OR L5: cloud/k8s/docker | `devops-engineer` | Infra changes beyond what git-ops handles need dedicated scope |
| L4: `security_risk ≥ MEDIUM` | `security-reviewer` | OWASP reviews need a dedicated agent that blocks merge on FAIL |
| L3: `has_public_api = true` | `api-contract-reviewer` | Breaking change detection requires a dedicated gate before merge |
| L3: `has_performance_sla = true` | `performance-reviewer` | SLA compliance needs systematic measurement, not ad-hoc checks |
| L4: `compliance_risk ≥ MEDIUM` OR regulated sector | `compliance-reviewer` | GDPR/SOC2/HIPAA/PCI requires a dedicated reviewer with standard references |
| L5: mobile in stack | `mobile-qa-reviewer` | Mobile quirks (touch targets, Safari compat) need systematic verification |
| L3: `ai_outputs ≠ "none"` | `ai-output-reviewer` | AI outputs need auditability and anti-leakage guarantees (triggers when `ai_outputs` is `content_generation`, `ranking_or_recommendation`, `automated_decision`, or `agent_action`) |
| L3: `qa_rigor ≥ MEDIUM` | `qa-verification-gate` | Pre-merge gate requires formal Verification Packages |
| L5: production deployment present | `release-smoke-auditor` | Post-merge/pre-prod health verification before promotion |

### What each optional agent does

**`test-engineer`** — Writes tests mapped to acceptance criteria IDs. Never updates expected outputs to make a test pass — must classify diffs as bug, intentional+versioned, or fixture defect first.

**`database-engineer`** — Writes migrations, optimizes queries, manages schema. Never runs DROP without explicit user confirmation. Every schema change requires a migration.

**`devops-engineer`** — Manages Dockerfile, docker-compose, CI/CD pipelines, IaC. No `terraform apply` or `kubectl apply` without explicit confirmation. Infra changes require post-apply smoke test.

**`security-reviewer`** — Reviews code for OWASP top 10, injection, auth flows, secrets exposure. Emits formal PASS/FAIL/WARN with CWE references. FAIL blocks merge.

**`api-contract-reviewer`** — Detects breaking changes (removed fields, changed types, auth changes). Requires version bump for any breaking change. Blocks merge on breaking change without bump.

**`performance-reviewer`** — Identifies N+1, missing indexes, bundle size regressions. Compares against SLA defined at intake. Reports benchmark deltas.

**`compliance-reviewer`** — Verifies the standard derived from the project's sector and risk (GDPR, SOC2, HIPAA, PCI). Checks data retention, consent flows, audit trails, encryption. Emits PASS/FAIL with section references.

**`mobile-qa-reviewer`** — Verifies touch targets ≥ 44px, no horizontal overflow, landscape/portrait behavior, iOS Safari and Android WebView compatibility.

**`ai-output-reviewer`** — Verifies AI outputs are auditable, deterministic with same inputs+version, don't expose model internals to frontend, have null/NOT_ELIGIBLE fallback paths.

**`qa-verification-gate`** — Gate before merge. Requires Verification Package (acceptance criteria, tests, regression statement). Emits APPROVED / NEEDS_WORK / BLOCKED. Never approves without evidence.

**`release-smoke-auditor`** — Post-merge pre-prod: verifies health endpoint, smoke flows, rollback readiness. Does NOT auto-promote. Requires all checks green before authorizing.

## Tier 3 — Domain agents

These agents are generated ad-hoc from the project's intake. The model analyzes:
- **L2 critical path**: the sequence of actions that must succeed for the project to have value
- **L3 structural flags**: subsystems with specialized domain logic

**Criterion for generating a domain agent**: a subsystem is in the critical path AND has domain logic not covered by `backend-engineer` + `frontend-engineer` alone.

**Limit: maximum 3 domain agents.** If more than 3 subsystems qualify, the model prioritizes by critical path position.

### Examples by sector

| Sector | Critical path | Domain agents generated |
|--------|--------------|------------------------|
| Fintech | Transactions → reconciliation → reporting | `transaction-engineer` |
| E-commerce | Catalog → cart → checkout → fulfillment | `checkout-engineer`, `catalog-engineer` |
| SaaS B2B | Tenant setup → billing → usage metering | `billing-engineer` |
| Healthtech | Intake → clinical logic → records | `clinical-logic-engineer` |
| PropTech | Search → valuation → contracts | `valuation-engineer` |
| EdTech | Content → progress → certification | `learning-progress-engineer` |
| Sports analytics | Data ingestion → signal computation → predictions | `prediction-engine-engineer` |

## How agents interact

The main Claude Code instance acts as a dispatcher. It reads `CLAUDE.md § Agent Dispatch` to decide which agent handles each task:

```
User request
     ↓
Main instance (reads task type)
     ↓
Delegates to agent (launches subprocess)
     ↓
Agent works in isolation (full context, defined scope)
     ↓
Returns result to main instance
     ↓
Main instance reports to user
```

Agents do NOT communicate with each other. Each operates with its own full context window. The main instance coordinates sequencing when tasks depend on each other.

## Placeholders resolved at generation time

When genesis-governance generates agent files, it replaces these placeholders with values from the intake:

| Placeholder | Source | Example |
|-------------|--------|---------|
| `{project}` | L1 project name | "PropAI" |
| `{packages.frontend}` | L5 frontend path | `src/app`, `packages/web/src` |
| `{packages.backend}` | L5 backend paths | `src/`, `packages/api` |
| `{stack.frontend}` | L5 frontend framework | "React/Vite", "Next.js" |
| `{stack.backend}` | L5 backend framework | "Node.js/Fastify", "Python/FastAPI" |
| `{stack.db}` | L5 database | "PostgreSQL", "MongoDB" |
| `{deployment.platform}` | L5 deployment target | "Render", "Vercel", "AWS ECS" |
| `{risk.primary}` | L4 primary risk (user's own words) | "users making decisions on stale data" |
| `{compliance.standard}` | Derived from sector + L4 | "GDPR", "SOC2", "HIPAA" |
| `{health.endpoint}` | L5 or governance.config.yaml | "/health", "/api/status" |

## How to add a new agent manually

If the generated set doesn't cover a subsystem you need:

1. **Create the file:** `.claude/agents/{name}.md`

   Use an existing agent as a template. Minimum required structure:
   ```markdown
   ---
   name: your-agent-name
   description: "Use this agent when [trigger condition] in {project}.
     Scope: [files it can touch]. NOT for: [explicit exclusions].
     <example>
     user: \"[typical request]\"
     assistant: \"I'll use the your-agent-name agent for this.\"
     </example>"
   model: claude-sonnet-4-6
   ---

   [Instructions for the agent: scope, constraints, delivery checklist]
   ```

2. **Add routing rule:** In `CLAUDE.md § Agent Dispatch`, add a row to the routing table:
   ```
   | [Situation] | your-agent-name | [Action] |
   ```

3. **Do NOT register in document registry** — agent files are operational config, not documentary artifacts.

---

## How to remove or disable an agent

Delete the `.claude/agents/{name}.md` file and remove its routing row from `CLAUDE.md § Agent Dispatch`.

There is no "disable" mechanism — agents are invoked by description match. If the file doesn't exist, the main instance falls back to handling the task itself.

## Model assignment rationale

| Model | Agents | Why |
|-------|--------|-----|
| `claude-opus-4-6` | `architect` | Design requires deep multi-layer reasoning |
| `claude-sonnet-4-6` | All implementation + review agents | Balanced capability for implementation, analysis, and code review |
| `claude-haiku-4-5-20251001` | `git-ops` | Commits, configs, and deps are low-complexity, high-volume operations — Haiku is faster and cheaper |

## Frequently asked questions

**Q: Can two agents touch the same file?**
A: Yes, but only one at a time. The main instance serializes agent calls. `backend-engineer` and `frontend-engineer` have non-overlapping scopes by design.

**Q: What if no agent matches a task?**
A: The main instance handles it directly. This is expected for cross-cutting tasks (reading docs, answering questions, coordination). It's a problem if it happens for implementation tasks — that means a needed agent is missing.

**Q: Should I commit agent files?**
A: Yes. `.claude/agents/` should be committed. These files define how Claude Code behaves in the project and should be version-controlled.

**Q: Can I use different models than the defaults?**
A: Yes. Edit the `model:` field in the agent's frontmatter. The default assignments are recommendations, not hard requirements.

**Q: Do agents from one project work in another?**
A: The files are portable, but they contain project-specific paths and constraints (via resolved placeholders). If you copy an agent to another project, review the `description` and body for hardcoded paths.
